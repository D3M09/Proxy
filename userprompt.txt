Implement player account capture + admin player manager in this PHP reverse-proxy project.

IMPLEMENTATION REALITY (corrected after reading the bundles):
- The app encrypts register/login REQUEST bodies (RSA-wrapped random AES key in the
  `Encryption` header; body = AES/Pkcs7 base64). The proxy only ever sees ciphertext,
  so it can neither rewrite nor read the plaintext payload server-side. There is no
  server-side rewrite of register POST bodies: the suffix is applied in the page shim
  BEFORE the app encrypts, and credentials are collected in the page and posted
  same-origin to /api/players-collect.php.
- Upstream RESPONSES are plaintext JSON (the axios response interceptor just returns
  e.data), so server-side response observation IS used for username/VIP/balance/login
  metadata. Confirm live keys with /api/player-probe.php before trusting them.
- REG_MOBILE_PATTERN is widened to accept both 11-digit and 12-digit (<mobile>7) input
  so the app's own client validator accepts the suffixed value.

FEATURE 1 - Register with mobile+7:
- When user enters BD mobile e.g. 01336710020, account username AND mobileNum become 013367100207 (input + trailing "7").
- Login uses the same suffixed number.
- (a) JS shim (playerShimScript(), wired into injectCombinedShims()) auto-appends "7" on
  desktop+mobile register forms, strips double-7, shows hint "Login ID will be <mobile>7".
- (b) DELETED: server-side rewrite of register POST bodies/JSON. Not possible on the
  encrypted endpoints (see IMPLEMENTATION REALITY). The shim is the mechanism.
- applyRegisterRules() / REG_MOBILE_PATTERN updated to accept 11 digits or 12-digit
  <11-digit-mobile>7 (11-digit inputs are auto-converted to 12 by the shim). Referral
  reg_info shim untouched.

FEATURE 2 - Store credentials in JSON (hashed):
- Proxy/data/players.json via store.php helpers: players_load(), players_save(), players_upsert().
- Schema per player: {id, username (suffixed), mobile_raw, mobile_suffixed, pass_hash (password_hash PASSWORD_DEFAULT), vault (AES-256-GCM), vip (default "VIP0"), balance (default 0), vip_override, balance_override, note, created_at, last_login_at, last_ip, user_agent, source: register|login|captured}.
- Capture happens client-side, BEFORE encryption: the shim posts the form values to
  POST /api/players-collect.php (same-origin, signed day-scoped nonce, per-IP rate
  limit). PHP hashes immediately. Plaintext is never logged or written.
- Server-side response observation (capturePlayerFromResponse()) fills username,
  last_login/last_ip/UA on /wps/session/login, and VIP/balance from /wps/member/info
  and /wps/wallets/* when the response carries a username.
- Atomic writes (store_write tmp+rename) behind a store_update() flock for concurrent
  upserts; dedupe by username. players.json is web-denied by data/.htaccess.
- isAuthTraffic() extended so register/login/member-info/wallet/player routes stay
  private, no-store.

FEATURE 3 - Admin panel player list:
- "Players" tab in Proxy/admin/panel_final3.php (created from the newest panel.php;
  admin/index.php requires panel_final3.php). Requires admin session + CSRF.
- Columns: Username (suffixed), Mobile raw, VIP Level, Balance, Created, Last login, IP.
  Search by username/mobile, pagination 50/page, sort by created/last_login.
- Effective VIP/balance = override if set, else captured; source badge shown. Manual
  vip_override / balance_override / note per row.
- "Refresh" is informational only (the proxy cannot query upstream without the player's
  session). Export CSV. pass_hash and the vault are never displayed or exported.

FEATURE 4 - One-click login (secure impersonation):
- Per-row "Login" button: POST + CSRF, admin-only, rate-limit 10/min, audit-logged to
  Proxy/data/admin_audit.json. Mints a single-use token (random_bytes(32) hex, 60s) in
  Proxy/data/player_login_tokens.json and redirects to /player-login?token=...
- /player-login (routed in Proxy/index.php + Proxy/router.php, isAuthTraffic, no-store,
  admin session required) burns the token, then serves the app's REAL /m/login page with
  a shim. The shim exchanges a separate short-lived single-use handoff id (30s) for the
  stored username+password ONCE via /api/player-credential.php, fills the genuine login
  form and submits it, letting the app's own crypto mint a fresh session; it then
  redirects to /m/home. The password is never in the URL, the HTML, or any log.
- Chosen solution: (i) encrypted reversible copy (openssl_encrypt AES-256-GCM, key
  'player_vault_key' in Proxy/config.php) used only for this auto-login and never
  displayed, plus form-driving so the app's crypto (not a replayed ciphertext) signs in.
- "Copy login ID" button as fallback.

CONSTRAINTS:

- Security: password_hash for storage, htmlspecialchars everywhere, CSRF on all POST,

- Preserve existing behavior: referral shim, brand rewrite, voucher, APK policy, splash,
